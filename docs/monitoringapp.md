# Shipping MonitoringApp logs to the stack

**Status: both components already speak the right protocol. Neither will
connect until three things are fixed.**

`~/Projects/MonitoringApp` has an `elastic` log sink in both the Java backend
and the Go agent. Both build ECS documents and POST them to Elasticsearch's
`_bulk` endpoint with the `create` action, which is the correct op type for a
data stream. That part needs no changes.

What stops it working is trust, credentials, and one naming detail.

---

## 1. Neither component trusts the stack's certificate  *(blocker)*

The stack uses a private CA generated by `stack/setup-certs.sh`. Nothing trusts
it by default, and the two components fail differently:

| | How it builds its client | What it trusts | Fix |
|---|---|---|---|
| Backend (Java) | `HttpClient.newBuilder()` with no `SSLContext` — `ElasticsearchAppender.java:118` | the **JVM** truststore | add the CA to a JVM truststore |
| Agent (Go) | `&http.Client{Timeout: ...}` — `internal/logging/elastic.go:70` | the **OS** trust store | `update-ca-certificates` |

Neither reads the other's store, so both need doing.

### Backend

Build a truststore that is a copy of the JDK's own plus our CA — copying rather
than editing `cacerts` in place keeps every public CA working and survives a
JDK upgrade:

```bash
sudo install -d /etc/monitoring-backend/certs
sudo cp ca.crt /etc/monitoring-backend/certs/elastic-ca.crt

JDK=$(readlink -f "$(which java)" | sed 's:/bin/java::')
sudo cp "$JDK/lib/security/cacerts" /etc/monitoring-backend/elastic-truststore.p12
sudo keytool -importcert -noprompt \
  -alias homelab-elastic-ca \
  -file /etc/monitoring-backend/certs/elastic-ca.crt \
  -keystore /etc/monitoring-backend/elastic-truststore.p12 \
  -storepass changeit
```

Then in `deploy/backend.service`:

```ini
Environment=JAVA_TOOL_OPTIONS=-Djavax.net.ssl.trustStore=/etc/monitoring-backend/elastic-truststore.p12 -Djavax.net.ssl.trustStorePassword=changeit
```

> Do **not** point `javax.net.ssl.trustStore` at a store containing only our CA.
> That setting replaces the default outright, so the JVM would stop trusting
> every public CA — and any outbound HTTPS the backend does would start failing
> with the same `PKIX path building failed` you were trying to fix.

### Agent

Go reads the OS store, so this is all it takes on each monitored host:

```bash
sudo cp ca.crt /usr/local/share/ca-certificates/homelab-elastic-ca.crt
sudo update-ca-certificates
```

## 2. No credentials are configured  *(blocker)*

`api-key`, `username` and `password` are all empty strings in
`application.yml` and `agent-config-example.yaml`. The appender warns about
this and then sends unauthenticated requests, which Elasticsearch rejects with
401.

Mint a key per component — each one can create documents in its own data
stream and do nothing else:

```bash
cd ~/elastic-logging/stack
./create-app-credentials.sh monitoring.backend
./create-app-credentials.sh monitoring.agent
```

Each prints an encoded key once. Paste it verbatim:

```yaml
# backend/src/main/resources/application.yml
monitoring:
  logging:
    sink: elastic
    elastic:
      url: "https://192.168.1.50:9200"      # was elastic.example.lan
      index: "logs-monitoring.backend-default"
      api-key: "<encoded key>"
```

```yaml
# agent config
logging:
  sink: elastic
  elastic:
    url: "https://192.168.1.50:9200"
    index: "logs-monitoring.agent-default"
    api_key: "<encoded key>"
```

The scoping is real, not decorative — a key issued for `monitoring.backend`
gets 403 on any other data stream and 403 on every read.

## 3. The backend reports a dataset that does not match its data stream

`logback-ecs-encoder` sets `event.dataset` itself, deriving it from
`serviceName`. With `<serviceName>monitoring-backend</serviceName>` it emits:

```json
"event.dataset": "monitoring-backend"
```

but the documents land in `logs-monitoring.backend-default`, whose dataset is
`monitoring.backend`. Nothing breaks, but the backend then appears under a
different name from every other source on any dashboard that groups by
`event.dataset` — including the **Log volume by source** panel.

One line in `backend/src/main/resources/logback-spring.xml`, inside the
`<encoder class="co.elastic.logging.logback.EcsEncoder">` block:

```xml
<eventDataset>monitoring.backend</eventDataset>
```

The Go agent does not set `event.dataset` at all, so the stack fills it in from
the data stream name and the agent needs no change here.

## What you do *not* need to fix

Two differences that used to matter are now handled by the stack, so leave the
application code alone:

- **Flat dotted keys.** Both components emit `{"log.level":"ERROR"}` rather
  than `{"log":{"level":"ERROR"}}`. The `logs@custom` pipeline runs a
  `dot_expander` over every document, so `_source` ends up nested and identical
  in shape to everything Elastic Agent writes.
- **Uppercase severities.** Both emit `ERROR`/`WARN`; Elastic Agent and the
  media-app parsers emit lowercase. `log.level` is a keyword field and keyword
  queries are case-sensitive, so a query for `log.level:error` would silently
  miss every MonitoringApp document. The same pipeline lowercases it centrally.

The Go agent's comment about upper-casing "so one query filters logs from both
components" is still true — it is just no longer the thing that makes it true.

---

## Verify

Restart both, then:

```bash
cd ~/elastic-logging/stack
source .env
curl -s --cacert certs/ca/ca.crt -u "elastic:$ELASTIC_PASSWORD" \
  "https://$STACK_IP:9200/logs-monitoring.*/_search?size=3&pretty" \
  -H 'Content-Type: application/json' \
  -d '{"_source":["@timestamp","event.dataset","log.level","log.logger","message"],"sort":[{"@timestamp":"desc"}]}'
```

You want `event.dataset` of `monitoring.backend` / `monitoring.agent`, and
`log.level` in lowercase. If nothing comes back, the appenders report their own
failures to stderr — `journalctl -u monitoring-backend | grep -i elastic`.

Common first failures:

| Message | Cause |
|---|---|
| `PKIX path building failed` | Step 1 — wrong store, or the JVM did not pick up `JAVA_TOOL_OPTIONS` |
| `401 Unauthorized` | Step 2 — key missing or pasted with whitespace |
| `403 Forbidden` | The key's dataset does not match the `index` in the config |
| `400 ... op_type create` | Only if you changed the appender — data streams accept `create` and nothing else |

## The alternative: let Elastic Agent collect it

Everything above wires the application's own appenders straight into
Elasticsearch. The other option is to have both components write ECS JSON to a
rolling file — `sink: file` with `format: json`, which they already support —
and let Elastic Agent read it.

That trades a little indirection for three real gains:

- **Buffering.** Elastic Agent queues to disk when the stack is unreachable and
  backfills afterwards. Both of MonitoringApp's own appenders drop events by
  design, and that is the right design for them — but it means an outage is a
  hole in your logs.
- **No secrets on monitored hosts.** No API key, no CA in a JVM truststore.
  This matters most for the Go agent, which runs on every monitored host and
  would otherwise need both distributed to each one.
- **`host.name`.** Elastic Agent stamps it. Writing to `_bulk` directly does
  not, so with a dozen hosts running the Go agent you cannot tell which one a
  line came from.

The cost is that the logs go via a file, and that a host already running an
Elastic Agent must have the collection added to its existing policy rather than
getting a second agent.

There is a ready-made prompt for doing this, covering the config changes, the
per-host install decision and the Fleet integration:
[monitoringapp-agent-prompt.md](monitoringapp-agent-prompt.md).
